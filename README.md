# Enclave Vaults: Client SDKs

Go and Rust client libraries for [Enclave Vaults](https://github.com/Privasys/enclave-vaults), Privasys's distributed virtual HSM running inside SGX enclaves.

The SDKs talk to a **constellation of independent vault enclaves** over RA-TLS. Each vault enforces a per-key `KeyPolicy`, performs typed HSM operations in-enclave (no raw key material on the wire), and seals state to its own MRENCLAVE. A typed key (wrap, sign, MAC) lives in one vault under that vault's seal. A secret stored with Shamir sharing is split k-of-n across the vaults, each holding one `RawShare`, which keeps it information-theoretically confidential below the threshold. A threshold Ed25519 key is generated by the vaults together, each holding one FROST share, and no vault or client ever holds the whole key.

The **vault directory** is a phonebook only: it returns `(endpoint, measurement)` tuples. It never sees keys, shares, policies, pending profiles, approvals, or audit data: the SDK does its own RA-TLS handshake and quote verification against each vault directly.

## Layout

| Language | Path                                          | Crate / module                                                   |
| -------- | --------------------------------------------- | ---------------------------------------------------------------- |
| Go       | [`go/vault/`](go/vault/)                      | `github.com/Privasys/enclave-vaults-client/go/vault`             |
| Rust     | [`rust/`](rust/) (crate `enclave-vaults-client`) | `enclave_vaults_client::client`                                |
| Go tool  | [`go/cmd/vaultprobe/`](go/cmd/vaultprobe/)    | `vaultprobe`, a per-member read-only probe (see below)           |

Both implementations expose two layers:

| Layer            | Type                                       | Responsibility                                                                                                                |
| ---------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Single vault     | `Client` (`Dial(ctx, registration, opts)` / `Client::dial(reg, opts)`) | RA-TLS handshake + quote verification against one vault, then the vault operations.                |
| Whole constellation | `Constellation` (`NewStaticConstellation(endpoints, opts)` / `Constellation::with_endpoints(endpoints, dial)`) | Dials each vault and fans calls out (Shamir distribution, pending-profile staging, promotion, revocation). |

Both implementations cover the basic operations. Threshold keys, binding v2 approvals, renewals, tombstones, vault identity and the raw policy calls are in the Go client only today.

## Vault operations

Each `Client` instance is a single RA-TLS session to one vault. The table names the Go methods; the Rust client has the snake_case equivalents of the basic operations.

| Operation | Purpose | Authenticator |
| --- | --- | --- |
| `CreateKey` | Create a typed key with its `KeyPolicy`, under a key-creation grant | Grant bound to the caller |
| `CreateKeyRenewal` (Go) | Create the next generation of a key: in place from a predecessor, or with the policy carried from another constellation | Grant + the key's owner or an enclave its policy names |
| `ExportKey` | Export raw material of an `exportable` key | Key policy, typically the owner's bound wallet approval |
| `DeleteKey` | Delete a key; the vault keeps a tombstone until the key's original expiry | Key policy, typically the owner's bound wallet approval |
| `DeleteKeyAfter` (Go) | Delete the old key of a migration or upgrade, bound to its successor | The owner's `delete_after` approval |
| `RetireKey` (Go) | Delete the previous generation after a renewal in place | An enclave the key's policy names |
| `ListKeys` | List live handles owned by the caller | OIDC |
| `GetKeyInfo` | Metadata + public components only (no sealed material) | Key principals |
| `Wrap` / `Unwrap` | AES-256-GCM with the sealed key; the vault generates the IV | Key policy (attested TEE or OIDC) |
| `Sign` / `SignPrehash` (Go) | ECDSA P-256, over a message the vault hashes or a pre-computed digest | Key policy (attested TEE or OIDC) |
| `Mac` | HMAC-SHA-256 | Key policy (attested TEE or OIDC) |
| `UpdatePolicy` | Replace the policy; respects `Mutability` | Key policy |
| `UpdatePolicyRaw` / `UpdatePolicyRawFrom` (Go) | Send a policy byte for byte (the stored form a binding v2 key needs); `...From` also binds the digest of the policy it replaces | Key policy |
| `GetPolicy` / `GetPolicyRaw` (Go) | The current policy + `policy_version` (raw: exactly as the vault serialised it) | Key principals |
| `CanonicalisePolicy` / `CanonicalPolicy` (Go) | A policy's digest, and its stored form | None |
| `GetVaultIdentity` (Go) | The vault's member id, billing id, MRENCLAVE, quote and capabilities; refused unless the connection pinned an MRENCLAVE | None |
| `IssueApprovalToken` | A manager mints a short-lived approval token for a specific `(handle, op)` | Manager OIDC |
| `ReadAuditLog` | Sealed append-only log; one entry per attempted op | Owner / auditor |

Pending-profile lifecycle (used during enclave upgrades) lives on the same `Client`: `StagePendingProfile`, `ListPendingProfiles`, `PromotePendingProfile`, `RevokePendingProfile`, and the matching `Constellation` methods that fan them out across the vaults that hold the key.

**Threshold Ed25519 keys (Go).** Threshold keys (FROST, RFC 9591) are client-orchestrated across the constellation: `Constellation.CreateThresholdKey` runs the distributed key generation, `Constellation.SignThreshold` collects a threshold of the vaults' signature shares into one EdDSA signature, and `ReshareThresholdKey` renews a key onto new vaults under the same handle and public key (`ReshareContext` is the digest the owner's wallet approval binds). The per-round calls (`FrostDkgRound1` ... `FrostAggregate`) are on `Client`. A creation or resharing that fails part-way aborts the keys its session committed, through the session, so the handle stays usable.

**Approvals (Go).** A key whose policy takes binding v2 approvals needs the members of its constellation on every approval-gated request: set `DialOptions.BindingMembers` to the vaults' member ids (from `GetVaultIdentity` over pinned connections), and the client sends them as `"binding": {"members": [...]}`. The owner's approval itself is their bearer: a passkey step-up from Privasys ID bound to that operation. `BindingV2`, `PolicyDigestJSON`, `UpdatePolicyFromTarget` and `DeleteAfterTarget` compute the same values the vault does, checked against the vault's own test vectors.

**Renewals and deletions (Go).** Generations of a name use the handle `<name>/gen-<n>`. A deleted key answers with an error matched by `IsKeyDeleted`; creating a deleted handle is refused (`IsHandleTombstoned`) until the key's original expiry, and a deleted name comes back only as a new key under `ReCreatedName(base, k)` (`<base>/new-<k>`), with the owner's create approval. `NewKeyCheck` computes the key check value a creator sends with a whole key.

## OIDC

By default the SDK works with JWTs from **Privasys ID** (`https://privasys.id`, JWKS at `https://privasys.id/jwks`). Each constellation's vaults accept one audience (Privasys production: `privasys-platform`; the test platform: `privasys-platform-test`), which the directory reports as `oidc_audience`: pass a token of that audience.

The vault matches the caller against the OIDC principals each key's policy names: a subject, optionally with `required_roles`, or a role alone. Bring-your-own IdP is supported by the vault binary (`oidc_issuer_url` + matching `Principal::Oidc { issuer }` in policies); from the SDK side, pass tokens minted by your IdP through the `AuthTokenSource` interface (Go) or trait (Rust).

## Go quick start

```go
import (
    "context"
    "fmt"
    "os"

    vault "github.com/Privasys/enclave-vaults-client/go/vault"
    "enclave-os-mini/clients/go/ratls"
)

func main() {
    ctx := context.Background()

    // 1. Dial options shared by every vault in the constellation:
    //    the OIDC token source and the RA-TLS policy that pins the vault build.
    var vaultPolicy *ratls.VerificationPolicy // expected MRENCLAVE, attestation server, ...
    dial := vault.DialOptions{
        AuthToken:   vault.StaticToken(os.Getenv("PRIVASYS_ID_JWT")),
        VaultPolicy: vaultPolicy,
    }

    // 2a. Talk to one vault directly.
    cli, err := vault.Dial(ctx, vault.VaultRegistration{Endpoint: "vault-1.example:8443"}, dial)
    if err != nil {
        panic(err)
    }
    defer cli.Close()

    sig, alg, err := cli.Sign(ctx, "tenant42/release-signer/gen-2", []byte("payload to sign"))
    fmt.Printf("alg=%s sig_len=%d err=%v\n", alg, len(sig), err)

    // 2b. Or fan out to the whole constellation (Shamir / pending profiles).
    con := vault.NewStaticConstellation([]string{"vault-1.example:8443", "vault-2.example:8443"}, dial)
    results, _ := con.StagePendingProfile(ctx, "tenant42/master-kek",
        vault.AttestationProfile{
            Name:               "app:v3 / SGX",
            Measurements:       []vault.Measurement{{Mrenclave: "a1b2…"}},
            AttestationServers: []vault.AttestationServer{{URL: "https://as.privasys.org/verify"}},
        },
        vault.PlatformBuild,
    )
    for _, r := range results {
        fmt.Printf("%s: ok=%v err=%v pending_id=%d\n",
            r.Vault.Host(), r.Success, r.Err, r.PendingID)
    }
}
```

## Rust quick start

```rust
use enclave_vaults_client::client::{
    AttestationProfile, AttestationServer, Client, Constellation, DialOptions, Measurement,
    PendingProfileSource, StaticToken, VaultRegistration,
};

fn main() -> anyhow::Result<()> {
    // 1. Dial options shared by every vault (set vault_policy to pin the vault build).
    let opts = || DialOptions {
        auth: Some(Box::new(StaticToken(std::env::var("PRIVASYS_ID_JWT").unwrap_or_default()))),
        ..Default::default()
    };

    // 2a. One vault.
    let reg = VaultRegistration {
        id: "vault-1".into(),
        endpoint: "vault-1.example:8443".into(),
        mrenclave: String::new(),
        mrsigner: String::new(),
        registered_at: String::new(),
        last_heartbeat: String::new(),
        status: String::new(),
    };
    let cli = Client::dial(reg, opts())?;
    let (sig, alg) = cli.sign("tenant42/release-signer/gen-2", b"payload to sign", &[])?;
    println!("alg={alg} sig_len={}", sig.len());

    // 2b. Whole constellation.
    let con = Constellation::with_endpoints(&["vault-1.example:8443", "vault-2.example:8443"], opts);
    let results = con.stage_pending_profile(
        "tenant42/master-kek",
        &AttestationProfile {
            name: "app:v3 / SGX".into(),
            measurements: vec![Measurement::Mrenclave("a1b2…".into())],
            attestation_servers: vec![AttestationServer {
                url: "https://as.privasys.org/verify".into(),
                pinned_spki_sha256_hex: String::new(),
            }],
            required_oids: vec![],
        },
        PendingProfileSource::PlatformBuild,
    )?;
    for r in &results {
        println!("{}: ok={}", r.vault.host(), r.result.is_ok());
    }
    Ok(())
}
```

## Shamir helper (`RawShare` keys)

The `RawShare` key type stores Shamir shares of an external secret (for example an app's KV master key held behind k-of-n SGX enclaves). Both SDKs ship the same finite-field implementation:

- GF(2⁸) with AES's irreducible polynomial `x⁸ + x⁴ + x³ + x + 1` (`0x11b`)
- Generator `g = 3`
- Per-byte independent random polynomial of degree `threshold − 1`
- Threshold ≥ 2, ≤ 255 shares total

Helpers: `vault.ShamirSplit(secret, threshold, n)` / `vault.ShamirReconstruct(shares)` (Go) and `enclave_vaults_client::shamir::{split, reconstruct}` (Rust). Tests: `cd go && go test ./vault/ -v` and `cd rust && cargo test`.

## vaultprobe

`vaultprobe` ([`go/cmd/vaultprobe`](go/cmd/vaultprobe/)) reads keys on every member of a constellation, one member at a time, for an independent view of what each vault holds. Per member and handle it prints `GetKeyInfo` (or the tombstone of a deleted key), the raw policy's version and SHA-256, and the audit log. With `-rules` it also prints each key's operation rules (ops, principal references, conditions); with `-tees`, the number of TEE principals with a SHA-256 per entry and of the operation rules; `-export-proof` presents one policy-change approval to `ExportKey` on each member and reports that every vault refuses it, and `-refuse` checks that each vault refuses a policy update not sent in stored form.

It holds no sign-in code and stores nothing: the two bearers (the key owner's for the vault audience, then one for the attestation server) are read from standard input, one per line, and kept in memory only. CI builds and publishes it on `vaultprobe-v*` tags (Windows and Linux binaries with `SHA256SUMS`).

```bash
{ privasys auth print-access-token --audience privasys-platform
  privasys auth print-access-token --audience attestation-server
} | vaultprobe -mrenclave <hex> -members host:port,host:port -handle <h> [-handle <h>] [-rules] [-tees]
```

## Trust model in one sentence

> The SDK trusts only attested vault enclaves it has handshaken with itself; it never trusts the directory for anything beyond endpoint discovery, and approvals travel SDK → vault end-to-end.
